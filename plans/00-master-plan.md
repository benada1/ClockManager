## 1. Goal

Build an employee time clock (Clock In / Clock Out) where **every punch time is trustworthy and
can be checked later**. The assignment asks for one hard rule (time comes from an external API in
`Europe/Zurich`). We treat that rule as the product's main idea: the system should **never record a
time it cannot justify**, and it should **never show the user information that is wrong or out of date**.

"Beyond the brief" here means depth, not more screens:

1. **Time you can verify.** Each punch stores which provider gave the time, the raw provider value,
   how long the request took (the uncertainty), and whether a second provider agreed.
2. **Rules the database enforces.** The DB blocks invalid states (two open shifts, clock-out before
   clock-in), not only the C# code.
3. **Repeated requests are safe.** Double clicks, retries after a network drop, and two open tabs
   all give exactly one record and a clear answer.
4. **Fail closed, and say why.** If time can't be trusted, the punch is refused with a specific
   reason. Nothing is recorded silently.
5. **Proof through tests.** DST, midnight, races and provider failures each have tests that run
   in CI.

## 2. Product scope

### In scope (MVP, built in depth)
| Area | What |
|---|---|
| Punch | Clock In / Clock Out for the signed-in employee. Server-side time only. Idempotent. |
| Status | Current state (open shift since X, elapsed time computed by the server), last punches. |
| History | The employee's shifts by day and week in Zurich time, with totals computed from UTC. |
| Anomalies | Shifts open too long ("forgotten clock-out"), very short shifts, shifts across DST, flagged, never changed automatically. |
| Manager view | List of employees with live status and flagged shifts. |
| Manager correction | Fix a wrong or missing punch **with a reason**. The original is kept and an audit row is written. |
| Trusted-time health | `/health/time` shows the status of each provider. The UI shows a banner when punching is blocked. |
| Auth (simple) | Seeded users, cookie auth, roles `Employee` / `Manager`. Enough that nobody can punch for someone else. |

### Out of scope (go into DECISIONS.md as "not done")
Payroll/overtime rules, breaks as a separate entity, geofencing/IP restriction, SSO/real identity
provider, offline punching (it can't be trusted, by design), multi-tenant, localization beyond
en/he display, mobile app.

## 3. Key architecture decisions (proposed; each goes into DECISIONS.md when built)

| # | Decision | Main alternative | Why |
|---|---|---|---|
| D1 | **Time is fetched from the provider for every punch** (no cached or extrapolated time for records). | Fetch once, then extrapolate with `Stopwatch`. | The rule says each punch is based on the external API. Extrapolation adds latency risk but blurs that guarantee. A cached value may be used **only** for the display clock, and it's labeled that way. |
| D2 | **Use the provider's UTC instant, then convert to Zurich with tzdb (NodaTime).** Check the provider's Zurich offset against the tz rules. | Read the provider's local Zurich date-time string. | A local time without an offset is **ambiguous during the repeated 02:00–03:00 hour in October**. A UTC instant never is. The provider's zone and offset are a cross-check, not the source. |
| D3 | **Primary provider + secondary provider**, with a cross-check when both answer (tolerance e.g. 2 s). | Single provider. | Covers provider outages and a provider that's "up but wrong". If they disagree beyond the tolerance, the punch fails closed with `time.providers_disagree`. Candidates: timeapi.io and worldtimeapi.org (or a similar API), chosen in plan 02 after a quick reliability check. |
| D4 | **Store `datetimeoffset` UTC instants + `ZurichOffsetMinutes` + `ZurichLocalDate` (the work date)**. | `datetime2` only. | Durations come from UTC. The work date is fixed at punch time (overnight shift = Zurich date of Clock In), so reports are stable and easy to query. |
| D5 | **Filtered unique index** `(EmployeeId) WHERE ClockOutUtc IS NULL` + `CHECK (ClockOutUtc > ClockInUtc)`. | App-level checks only. | Races between two tabs or two servers can only be stopped for sure by the DB. |
| D6 | **`Idempotency-Key` header** (UUID generated by the client per punch *attempt*), stored with a unique index. A repeat returns the original response. | Rely only on 409. | A retry after a lost response should succeed, not show a confusing "already clocked in". |
| D7 | **Monotonic guard**: a new punch time must be ≥ the employee's last punch (within a small tolerance), or it's rejected with `time.went_backwards`. | Trust the provider. | Catches provider skew between primary and secondary, and providers going back in time. |
| D8 | **Corrections never change a punch in place.** `ShiftCorrection` rows (old value, new value, who, when, why); the shift shows the effective value. | Edit in place + log. | Full audit history; reviewers can see the original. Correction *timestamps* (the "when") also come from the trusted clock. |
| D9 | **ProblemDetails with stable codes** (`shift.already_open`, `shift.not_open`, `time.unavailable`, `time.invalid_response`, `time.providers_disagree`, `time.went_backwards`, `idempotency.key_reused`). | Free-text errors. | The UI maps codes to clear messages; tests assert on codes. |
| D10 | **JWT in an HTTP-only cookie**, open signup (Employees only), hashed passwords via `PasswordHasher<T>` (changed by the user 2026-11-18, D-049). | ASP.NET Identity / JWT. | Smallest thing that makes "who punched" trustworthy. JWT in localStorage is worse for a browser-only client. |

## 4. Edge cases and "misinformation" scenarios to cover

Each one gets: how it's handled → which test proves it → a DECISIONS.md entry.

### Time and calendar
- **DST spring forward** (last Sun of March, 02:00 → 03:00): shift 22:00–06:00 = **7 h**, not 8.
- **DST fall back** (last Sun of Oct, 03:00 → 02:00): shift 22:00–06:00 = **9 h**. A punch at
  02:30 the "second time" stays a separate instant (D2). Display shows the offset (`+01:00` / `+02:00`) when it's ambiguous.
- **Overnight / midnight**: shift belongs to the Clock In date. The weekly report puts a Sunday→Monday
  shift in the week of the Clock In. Documented, and tested at week and year boundaries (Dec 31 → Jan 1).
- **Leap seconds**: ignored (providers smear or ignore them). Documented as a limit.
- **Server machine in a different timezone / wrong clock**: there must be no effect on records.
  Test: run the integration suite with the process TZ set to e.g. `Pacific/Kiritimati`.

### Time provider
- Timeout, 5xx, 429 (rate limit), DNS failure, TLS failure → try the secondary → otherwise 503 `time.unavailable`.
- 200 with garbled JSON, missing fields, a wrong zone (`Europe/London`), an offset that doesn't
  match the tz rules for that instant, or a year that's way off → `time.invalid_response`, **don't** try to "fix" it.
- Slow response (inside the timeout but high latency) → round-trip time is stored. Above a threshold
  (e.g. 1.5 s) the punch is accepted but flagged "low precision" (decided, see §7).
- Primary and secondary disagree → fail closed (D3).
- Provider time earlier than the last punch → `time.went_backwards` (D7).
- Provider returns a stale/cached response (same time on two calls) → detected by the monotonic guard and by comparing with elapsed `Stopwatch` time; logged.

### Concurrency and repeated requests
- Double click → the button is disabled + idempotency key → one record.
- Two tabs both clock in → one wins, the other gets 409 `shift.already_open` + the current state; the UI refreshes.
- Retry after a lost response → same idempotency key → same 201 response replayed.
- Same idempotency key reused with a *different* intent → 422 `idempotency.key_reused`.
- Clock Out racing a manager correction of the same shift → optimistic concurrency (`rowversion`) → 409.
- Load test: N parallel clock-ins for one employee → exactly 1 succeeds (integration test with real SQL Server).

### Business-rule edges
- Clock Out without an open shift → 409 `shift.not_open`.
- Forgotten clock-out: shift open longer than `MaxShiftHours` (config, default 16) → flagged in status/manager view.
  The employee can still clock out (the real time is recorded, flagged), or a manager corrects it.
  **Never auto-closed with a made-up time.**
- Very short shift (< 1 min, e.g. accidental double punch on two devices) → recorded, flagged "possible accidental".
- Employee deactivated while a shift is open → can't punch any more. The manager sees the open shift and must resolve it.
- Corrections that would overlap another shift, or put clock-out before clock-in → rejected.
- Corrections in the future → rejected (compared with *trusted* time).

### UI "misinformation" risks
- Elapsed timer drifts from the server → the UI computes elapsed time from **server-provided
  `serverNowUtc` + clock-in**, re-synced every minute, and labeled "server time". The browser clock is never used as a time source.
- Stale state after the laptop sleeps or a tab is in the background → refetch status on `visibilitychange` / focus.
- Offline → clear "offline: punching unavailable" state, no queued punches.
- 503 → banner explaining *why* (provider down vs. disagreement), with a retry button (same idempotency key).
- Times always shown in Zurich with the zone label, even if the user's browser is in another zone.

### Who builds what

No single agent builds everything. The **main Claude Code session is the coordinator**: it writes
the phase plan, gets approval, sends each step to the agent that owns that area, checks the result
with `/verify`, and makes the commit. Subagents don't call each other, so every hand-off between
areas goes through the main session as a written contract (endpoint shape, schema change, failing test).

| Phase | Lead agent | Supporting agents | Hand-off out of the phase |
|---|---|---|---|
| 0 Foundations | main session | backend (test project, middleware) | Agent files, solution, CI green |
| 1 Trusted clock | **backend** | qa (provider-failure tests) | `ITrustedClock` + `TrustedInstant` contract |
| 2 Schema | **db** | qa (constraint tests) | Entities, migration, seed data, fixture |
| 3 Punch API | **backend** | db (index/transaction review), qa (race + replay tests) | OpenAPI contract for `/api/punches`, `/api/me/status` |
| 4 Auth | **backend** | db (`Employee` credentials column), qa | Login/logout contract, roles |

**qa** writes the failing tests from the plan's test list → **backend** makes them pass → the main
session runs `/verify` and commits. The qa agent writes tests but never changes production code.

## 6. Risks
| Risk | Mitigation |
|---|---|
| Free time APIs are unreliable or rate-limited (worldtimeapi in particular has a history of outages). | Two providers, health endpoint, clear 503 in the UI; document it as a known limit; never fall back to the local clock. |
| LocalDB isn't available in CI (Linux). | CI uses a SQL Server container; tests read the connection string from an env var. |
| Scope creep (the manager area can grow large). | Phases 1–5 are the must-have core; 6–7 are cut to the minimum if time runs short and the cut is recorded in DECISIONS.md. |
| Auth adds complexity that isn't the focus. | Keep it minimal (D10); no registration or password reset. |

## 7. Resolved questions (answered 2026-11-17)
1. **High provider latency (> 1.5 s):** accept the punch, store the round-trip time, flag it "low precision".
2. **Forgotten clock-out (> 16 h):** the employee can clock out themselves; the real trusted time is recorded and the shift is flagged for manager review.
3. **Auth:** minimal cookie auth with seeded users and roles (D10).
4. **Playwright e2e:** only if Phases 1–7 finish early; otherwise listed as "not done" in DECISIONS.md.
