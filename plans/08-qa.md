# 08 — Wide QA pass

**Status:** Approved 2026-11-18 with changes: **Phase 7 is built first**, then this one wide QA covers everything · no Playwright for now · no screenshots in the repo · desktop first (the app is used on a PC) · **Agents:** qa (several runs), backend and frontend (fixes)
**Why this is wide:** Phases 1–3 had a full qa pass (QA-01 to QA-26). Phases 4, 5, 6 and the punch-screen redesign had none, nobody has seen the
screens in a real browser, and several small items are still open. This pass covers all of it, then the whole app once more as a whole.

## 1. Goal
Find the problems a reviewer or a real user would find, **before** they do: broken flows, wrong numbers, unsafe behavior, confusing screens,
doc steps that don't work from a clean clone. Everything real gets fixed (own commit, test that fails without the fix) or written down as a known limit.

## 2. Areas and what each one checks

### A. Login and security (Phase 4, never QA'd)
Signup/login input (huge, unicode and look-alike names, spaces, case, very long passwords and the hashing cost) · username enumeration through signup and timing ·
cookie flags, expiry, logout, tampered/expired/other-key tokens, `alg:none`, role in the token vs the database · deactivated user with a live token ·
rate limits (per IP, NAT, behind a proxy, the 429 body and header) · double signup race · CSRF with `SameSite=Lax` (cross-site POST, non-JSON bodies, `OPTIONS`/`HEAD`) ·
secrets in logs, responses and git history · seeded manager password flow · startup without a key. Plus a run of the **security-review** skill over the whole repo.

### B. Real browser checks (Phase 5 + punch redesign + History, never seen)
Checks are code-based (no browser tool for now, user decision): read every screen and state from the code and the `dev:mock` scenarios, desktop first, and give the user a short manual list to look at the screens:
signup, login, punch (clocked out / in / forgotten / long / no-time / every error banner), History (normal, empty, error, DST week, overnight, open shift).
Also, by reading the code and the tests: keyboard-only use and focus order, contrast of the theme colors, text overflow of the big counter, two tabs
(second tab clock in → 409; state refresh on focus), offline and back, session expiry while the page is open, double-click, slow network, the `dev:mock` scenarios,
the production build (`npm run build` + preview).

### C. Whole-stack flows on the real backend (Phases 3–6 together)
Sign up → clock in → second tab → clock out → History shows it → log out → expired session, with the **real database and real time providers**
(published backend copy on a spare port, never the user's running API). Time provider down (config switch or a stub host) → 503 banner and Try again.
Session cookie through the Vite proxy. Server in another time zone/culture. A week with real DST data through the UI.

### D. History and numbers (Phase 6, never QA'd)
Week edges, Monday/Sunday, DST weeks, year boundary, overnight, default-week ties, open shifts, thousands of shifts (query time and the index in use),
totals vs the punch responses and the status flags (same flags everywhere), another user's data, bad dates and culture, server in another zone.

### E. Gaps left from Phases 0–3
The open follow-ups (the `/health/time` alias behind `/api`, QA-25 log line), the status endpoint under the new login, idempotency records growing (cleanup plan),
migrations from an empty database and from each step, CI health (all jobs, the SQL container, the exotic-time-zone run), dependency audit
(`npm audit`, `dotnet list package --vulnerable`), unused code and files.

### F. Documentation and process (what reviewers read)
**Clean-clone test:** follow the README exactly on a fresh clone and fresh database (SQL Express, LocalDB and Docker options, user-secrets, both servers) · README vs reality ·
every DECISIONS entry has a real reference, every edge-case row points at a test that exists, the corrections table and worklog are complete ·
CLAUDE.md matches the stack (Tailwind, Vitest, cookie JWT) · plan statuses · agent files · commit history review (message style, one task per commit) · short-comment rule.
A final independent **code-review** of everything since Phase 3 at high effort.

## 3. How it runs (so it stays fast and nothing collides)
| Wave | Runs | Notes |
|---|---|---|
| 1 | **A** (backend qa, own build folder) · **B** (frontend qa, code-based) · **F + E docs/dependency audit** (read-only, no builds) | In parallel: different folders, no shared build |
| 2 | **D + C** (backend qa, then browser flows against a published copy on a spare port) | After wave 1 so fixes don't move the target |
| 3 | Fixes: backend and frontend agents, **one `fix:` commit per finding**, test that fails first | Severity order; CI checked after every push |
| 4 | Final: full `verify`, exotic-culture run, CI, clean-clone README test, code-review + security-review, summary | |
- Every agent reports findings in the usual format (id, severity, repro, expected/actual, suggested fix) and writes **failing tests or repro steps**, never fixing in the same run.
- **Severity rule:** critical, high and medium are fixed; low is fixed if cheap, otherwise recorded in DECISIONS.md as a known limit.
- Agents never touch your running API on 5258 or your Vite on 5173; they use their own build folders and spare ports and stop what they start.
- Short comments and short commit messages, as agreed. Expect roughly **8 to 10 agent runs** in total.
